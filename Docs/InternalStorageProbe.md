# Milestone 1: internal-storage launch probe

This temporary, opt-in probe tests only `1941.zip`. It uses the existing `UrlSchemeGenerator.GetUrl()` and awaits `Launcher.LaunchUriAsync()`. It never opens or enumerates RetroArch's private storage. Existing library launch code, including its ROM preflight check, is unchanged.

When enabled, the probe screen runs before normal USB/theme/library initialization. It does not change themes or library navigation. With the configuration absent or `Enabled=false`, normal startup runs as before, including its existing USB requirements. Do not disable the probe until a normal library/theme setup is available if you want to use the normal UI.

## Obtain the exact values on Xbox

1. In the installed RetroArch, manually load the working MAME core and `1941.zip` from its private `LocalState/roms/arcade` directory. Confirm gameplay first; record the RetroArch version and package identity from Device Portal. Do not infer the DLL filename from the displayed core name.
2. Enable RetroArch's logging verbosity and logging to file if those settings are available in your build. Note its configured log directory. Restart RetroArch, manually load the game again, and retrieve its log using Device Portal's access to that RetroArch package. Look for the complete content path and the core library load path. Labels and log locations vary by build.
3. Alternatively, inspect the game's full path in RetroArch's file browser or a playlist generated by RetroArch. Use a playlist path only if it is fully qualified. Inspect the installed core directory through RetroArch or Device Portal to identify the actual loaded DLL. A log showing which DLL loaded is stronger evidence than merely finding several MAME DLLs.
4. `RomPath` must be the full Windows drive path **as seen by RetroArch**, ending in `\1941.zip`, with backslashes. Do not substitute a Device Portal REST URL, package-relative transfer path, `ms-appdata:` URI, guessed drive letter, or just `roms/arcade/1941.zip`.
5. `CoreFileName` must be the exact loaded DLL's basename, including `.dll`. The existing generator supplies `cores\` before it. Confirm the installed RetroArch accepts that core location; this probe deliberately retains the current launch contract.

If the installed build cannot expose these values, stop and obtain diagnostic evidence from that build rather than guessing. These instructions do not grant LaunchPass access to RetroArch's files.

## Windows build and deployment

1. Open `LaunchPass/LaunchPass.sln` on Windows in Visual Studio with the UWP C# development tooling. The project requests Windows SDK `10.0.20348.0`; install that SDK and the tools needed for .NET Native Release builds. Restore the project's existing NuGet dependencies. A macOS .NET SDK cannot build the complete UWP application.
2. Select **Release / x64**. In the package manifest's Packaging settings, select or create a signing certificate matching the manifest publisher. The checked-in temporary certificate may not be usable on another machine. Keep RetroArch's package unchanged. Be aware that another installed frontend owning `launchpass:` can interfere with the return callback; record which frontend packages are installed.
3. Use **Publish > Create App Packages**, select sideloading and x64, then build. Install the generated app bundle and its required x64 dependency packages through Xbox Device Portal. Follow Device Portal's existing trusted installation workflow. A successful compile/install does not prove protocol activation or game loading.
4. Copy [InternalStorageProbe.example.xml](InternalStorageProbe.example.xml) to a local file named **InternalStorageProbe.xml**. Fill `RomPath` and `CoreFileName` with the measured values. Preserve `<Enabled>true</Enabled>`. XML-escape special characters such as `&` as `&amp;`; backslashes are literal and should not be doubled.
5. Upload the file to **LaunchPass's own LocalState root** using Device Portal, not RetroArch's LocalState. It sits beside `InternalStorageProbe.log`, not in LocalCache and not inside the installed app package. The example is documentation only; it is not automatically packaged or enabled.
6. If Device Portal does not expose LaunchPass's data folder until first activation, start it once, terminate it, then upload the configuration and relaunch. That first unconfigured start may hit the existing USB startup failure. No USB is required once the valid enabled probe configuration is present.
7. Fully terminate and relaunch LaunchPass after editing the configuration. It is loaded at activation; an already-displayed probe page keeps its configuration until the process restarts. Disconnect USB for the no-drive test. The probe button should be focused; use a normal Xbox controller or keyboard if X-Arcade focus/select mappings are not yet known.

No automatic launch occurs on startup or return. Press the probe button to issue each request. Empty values and invalid paths/core names are rejected before any protocol request. A malformed XML configuration displays a diagnostic probe page and cannot launch.

## Diagnostics and interpretation

Download **LaunchPass LocalState/InternalStorageProbe.log** through Device Portal after each run. The screen displays the full log location. Logging is independent of the normal Settings logging switch and `RetroPass.log`. It appends UTC timestamps, attempt IDs, the generated URI, the URI passed to Windows, activation results/exceptions, and lifecycle events. Each entry closes the file after appending. Log-write failures are sent to debugger output and shown after a probe attempt.

- `LaunchUriAsync result=True`: Windows reports activation of the registered handler. This does **not** establish that RetroArch loaded the core or ROM, or even that the intended package owns the scheme. Verify visually and with RetroArch logs. [Microsoft Launcher API](https://learn.microsoft.com/en-us/uwp/api/windows.system.launcher.launchuriasync)
- `result=False`: Windows did not report successful activation. Check handler registration and the installed package.
- `validation/activation error`: inspect the exception and URI. The probe makes no target-file existence check.
- `activation requested` without a result: outcome is unknown. Suspension/termination can prevent the awaited continuation from logging; correlate lifecycle events and RetroArch observations rather than inferring success or failure.
- Lifecycle records include launch/activation kind, previous execution state, callback URI, window activation/visibility, background transitions, resuming, suspending, and unhandled exceptions. OS process termination has no guaranteed final event. Their order can differ by Xbox execution state.

Upstream RetroArch UWP parses this protocol and ignores new `cmd` arguments once initialized; it implements `launchOnExit`. The installed Xbox package may differ. Do not add `forceExit`, file permission changes, or another launch mechanism as part of this test. [RetroArch UWP implementation](https://github.com/libretro/RetroArch/blob/master/uwp/uwp_main.cpp#L692)

## Xbox hardware checklist

Record firmware, RetroArch package/version, core filename, ROM path, LaunchPass build, whether a debugger is attached, and USB presence. Preserve both applications' logs. For each attempt, record activation result separately from observed core/ROM load and gameplay.

- [ ] Baseline: manually loading this ROM with this core succeeds in RetroArch.
- [ ] Cold launch: fully quit RetroArch and LaunchPass, remove USB, start LaunchPass, and confirm the probe appears. Press once. Save the generated URI and result; confirm RetroArch loads `1941.zip` with the intended MAME core and gameplay starts.
- [ ] Return: use RetroArch's normal **Quit RetroArch** action, rather than merely Close Content. Confirm the `LaunchPass:` callback reaches this fork and the probe reappears. Collect activation/resume/window events; if callback fails, manually return and record that separately. Do not treat manual return as callback success.
- [ ] Repeated launch: after quitting back to the probe, launch the same ROM at least three times. Confirm gameplay each time and distinct attempt IDs/results. Record whether RetroArch fully exited between attempts.
- [ ] Already-running case: leave RetroArch initialized, manually switch to LaunchPass without quitting RetroArch, then press the probe. Record whether RetroArch ignores the new content request. Successful activation alone is insufficient.
- [ ] Restart case: terminate LaunchPass while RetroArch is running, then quit RetroArch. Verify cold protocol activation can reconstruct the probe from its configuration. Repeat after an Xbox reboot.
- [ ] Invalid configuration: in separate runs, try an empty value, a relative ROM path, a different ROM filename, and a core path instead of basename. Confirm validation errors and no `activation requested` record. Restore the measured values afterward.
- [ ] Receiver failure: optionally configure a syntactically valid nonexistent DLL basename, keeping the real ROM path. Confirm the log never claims game-load success even if activation returns true. Restore the correct core and fully quit RetroArch before retrying.
- [ ] Existing-library regression: with a known-working USB library/theme setup, terminate LaunchPass, remove/disable the probe configuration, and relaunch. Confirm normal library navigation and external ROM launching remain functional. An inaccessible/missing external ROM must still fail the existing preflight check.

Milestone 1 is proven only when the actual Xbox runs the private `LocalState` ROM through this fork and the observation is recorded. Builds, validation checks, and activation booleans alone are insufficient. Record return/repeat failures as limitations even if the first cold launch succeeds.

## Changed files and remaining risks

Local verification: 28 portable checks passed against the actual probe configuration and existing URI generator using a temporary .NET harness with UWP stubs. They covered valid/invalid configuration, XML template loading, absent configuration, and URI argument round trips for spaces, ampersands, plus signs, percent signs, and hashes. Project/example XML and `git diff --check` passed. Existing external launch, library loading, main UI, URI generator, and manifest files were checked unchanged against HEAD. These checks do not validate UWP API binding, Windows compilation, Xbox lifecycle behavior, or game loading; those remain pending.

- `LaunchPass/InternalStorageProbe.cs`: opt-in XML configuration, validation, fixed test entry, existing URI generator call, awaited activation, small probe page, and persistent diagnostics.
- `LaunchPass/App.xaml.cs`: probe gate before normal startup/activation plus opt-in lifecycle diagnostics. No general theme fallback or navigation rewrite.
- `LaunchPass/LaunchPass.csproj`: explicit compile inclusion for the new C# file.
- `Docs/InternalStorageProbe.example.xml` and this guide: configuration template and test/deployment procedure.

Remaining risks: installed protocol/core-path compatibility; runtime path stability across RetroArch installation changes; suspended/already-initialized behavior and callback registration conflicts. The probe validates syntax only and cannot verify private file existence. Its exact DLL filename requirement matches the current generator and may expose incompatibilities in a differently packaged RetroArch. No sandbox capability or permission changes are made. No commit is part of this work.
